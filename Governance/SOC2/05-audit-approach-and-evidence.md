## 1. Purpose

How Ayka will run a SOC 2 examination when the [readiness assessment](04-readiness-assessment.md) allows it: choosing the auditor, setting the period, collecting evidence, and keeping records. Section 7 holds the record templates. **No record entries exist**; each template is filled only when the activity happens.

## 2. Choosing the service auditor

1. Only a licensed CPA firm can issue an AICPA SOC 2 report. Many German audit firms offer the equivalent assurance under ISAE 3000 using the Trust Services Criteria, or issue SOC 2 through a US-licensed member firm. Ask which standard the report is issued under and whether the customer base accepts it (**to verify** with each firm).
2. Ask for a firm that also audits BSI C5 or ISO/IEC 27001; one evidence set can then serve several reports.
3. Independence: the firm that issues the report must not also have designed or operated Ayka's controls. A readiness review by the same firm is acceptable only as advice.
4. Request a fixed-fee proposal covering Type I and the first Type II, the PBC list format, the sampling approach and the evidence portal.

## 3. Report period and timing

| Item | Plan |
|---|---|
| Type I | As of a single date after the readiness check (roadmap phase 5) |
| First Type II period | 6 months, starting the day after the Type I date |
| Later periods | 12 months, contiguous, so customers always have a report less than a year old |
| Bridge letter | Issued by Ayka management for the gap between period end and report date, on customer request |

## 4. Provided-by-client (PBC) list process

1. The auditor sends a PBC list per control. Compliance and Risk logs each request in the evidence tracker with control ID, requester, due date and owner.
2. The control owner supplies evidence from the system of record (Git, GitHub, AWS, Entra ID, HR system). Screenshots show the date and the account; exports keep the original file.
3. Compliance and Risk checks completeness against the request and the control description before upload. Nothing is edited after export.
4. Population lists (all merged pull requests, all joiners and leavers, all incidents in the period) are generated by query, and the query is supplied with the list so the auditor can re-perform it.

## 5. Typical sample sizes

The auditor decides sample sizes. Common practice for Type II, used here for planning:

| Control frequency | Typical sample |
|---|---|
| Annual | 1 |
| Quarterly | 2 |
| Monthly | 2 to 3 |
| Weekly | 5 to 10 |
| Daily | 20 to 40 |
| Many times a day, or per event | 25 to 60, or 10 % of the population |
| Automated | 1, with reliance on IT general controls (change management and access over the automation) |

Automated controls (for example CA-02 fail-closed evaluation, CM-03 severity routing) are tested once by inspection and re-performance, provided the change controls over the code that implements them (CM-01 to CM-05 applied to `.github/` and the scripts under `CODEOWNERS`) operate for the whole period. This is why CM-05, independent approval, matters beyond change management itself.

## 6. Evidence sources and retention

| Evidence | System of record | Retention needed | Today |
|---|---|---|---|
| CI evidence bundles (`compliance-evidence`) | GitHub Actions artifacts | Period + 12 months (18 months minimum) | 90 days: gap G7. Plan: copy to an S3 bucket with Object Lock in compliance mode |
| Pull requests, reviews, approvals | GitHub | Life of the repository | Kept |
| Environment approval history | GitHub deployments | Period + 12 months | Kept by GitHub; export each quarter |
| Ruleset configuration | GitHub | Change history over the period | Export at start, end and on every change |
| CloudTrail logs | S3 trail bucket | 1 year online, 6 years archive (HGB/AO for business records where relevant) | Designed only |
| Access reviews, vendor reviews, restore tests, incident records | Evidence tracker | Period + 12 months, then per the retention policy | None yet |

## 8. Management representation letter

At the end of fieldwork the Managing Director signs a representation letter for the auditor, confirming among other things that the description is fair, that all known incidents and deviations were disclosed, and that subsequent events were reported. Ayka signs it only after the CISO confirms each statement against the incident log, deficiency log and change history.
