## 1. Conclusion

**Ayka is not ready for a real SOC 2 Type I and should not engage an auditor yet. Nothing is deployed.**

Version 1.1 changed the paperwork position, not that conclusion; version 1.2 adds the infrastructure work of the same day (detection, backup, evidence archive, Region, platform roots in the gate), which is Terraform that is scanned, not a running system. Since version 1.0 every control in the matrix has a written design (no control is Planned), a Type I test walk-through exists for all 65 controls ([SOC2-06](06-type1-readiness-pack.md)), a log of automated-control evidence has been started ([SOC2-07](07-observation-period-log.md)), and the first real monthly change review has been run ([REAL-SOC2-001](../records/real/soc2/REAL-SOC2-001-change-review-2026-10.md)). That review also found that the push runs on `main` have been red or waiting since 2026-10-05 (new gap G14). Against a Type I as of 2026-11-10 the pack expects 13 controls to pass, 33 to fail for lack of an operating instance or because the Terraform contradicts them, and 19 to be untestable without a deployed system or because they are carved out.

The reason for the conclusion is not paperwork. A SOC 2 examination reports on a system that runs, and the Ayka Portal has never been deployed: the pipeline applies nothing (`SIMULATED APPLY`), the workload uses mock credentials, and the platform roots have never been applied. An auditor can test the change-management pipeline today, but a report on the pipeline alone would not answer any customer's question about the service.

What is already strong is unusual for a company this size: every change to the `ayka-portal` workload is scanned by three tools against 38 mapped rules, decided fail-closed, recorded in a checksummed evidence bundle, and the gate proves on every run that it still catches known-bad configurations. Those controls (CA-01, CA-02, CM-01 to CM-04, MO-01, IC-01) would pass a Type I design test now and generate Type II evidence automatically, with one caveat found on 2026-11-10: the `apply` job that holds CM-04 has not completed in CI since 2026-10-05 (G14). The platform roots are now scanned by a separate `Platform Gate` job (G12), but that job has not run on GitHub and is not a required check, so it does not yet count as a control that blocks a merge.

## 4. Non-blocking observations

- The gate's control mapping was ISO-only on 2026-10-06. It now carries a `soc2` list per rule in `control-mapping.yaml` (38 rules), and the compliance report prints the criteria a run touches. A criterion there is supported by a plan check, not met by it.
- `exceptions.yaml` has 111 entries in five roots (60 landing zone, 20 `aws-iam-core`, 14 `ayka-portal`, 14 `remote-state`, 3 `evidence-archive`), each with a reason, an owner and an expiry, scoped to one root. Expiry dates are staggered over 21 dates from 2027-01-08 to 2027-11-26, so no single day brings all findings back; two portal entries (`CKV_AWS_144`) still expire on 2027-03-31. Eight entries expire after 2027-11-10, more than 12 months from the date of this assessment, which the monthly change review (SOC2-08, section 3.3 step 3) would query. Several entries are open work, not false positives (broad IAM grants, no access logging on the log, state and evidence buckets).
- `S3_REPLICATION_DISABLED` is LOW and open. For a 99.5 % availability target this is acceptable; if the commitment rises, cross-Region backup copies become necessary.
- The personnel register has 24 people while most real control evidence points at one maintainer. For an actual audit, every role holder in the description must be a real person who can be interviewed.
- With 24 staff, Ayka is below the 50-employee threshold of the German Whistleblower Protection Act (HinSchG). A reporting channel (IC-03) is still good practice and helps CC2.2.
