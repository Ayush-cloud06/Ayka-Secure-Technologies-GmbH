> Ayka Secure Technologies GmbH is a simulated company and `ayka-portal` has never been deployed. This document is design only. A design is not a record that the control runs.

## 1. Purpose and how to read it

Until 2026-11-10, 19 controls in the [control matrix](03-control-matrix.md) were **Planned**: no design existed for them. This document gives each of them a specific design, or points to the document that holds it. With a design in place the matrix status becomes **Designed** (written down, not gated, not deployed). Nothing here moves a control to **Implemented**.

Each design states what the control does, who operates it and when, which record it leaves, and the test that decides whether it is *operating*, which is what a Type II auditor would sample. The tests are repeated per control in the [Type I readiness pack](06-type1-readiness-pack.md).

Two rules apply to every design:

1. A record is written when the activity happens, by the person who did it. Nobody writes a record for something that did not occur ([README](README.md#6-rules-for-these-documents)).
2. Where one person holds several roles, the design says so and names the compensating step. It never pretends the roles are separate.

## 3. Compensating monthly change review (CM-05, G3)

### 3.1 Problem

Control CM-05 says the person who approves a change is not its author. The repository has one maintainer, the ruleset `protect-main` requires 0 approvals, and both approval environments allow self-review. Requiring an approval from a second person is impossible today and would block every change. Gap G3 in the [readiness assessment](04-readiness-assessment.md) therefore calls for a **compensating detective control**: a monthly retrospective review of every merged change. It finds what an approver would have seen, after the fact. It does not prevent anything, and it does not meet CM-05.

### 3.2 Operator and independence

| Item | Rule |
|---|---|
| Operator | The Managing Director role. In the simulated company that is a different person from the authors. In the real repository the repository owner holds every role, so the reviewer is the author. Each record must say which is true |
| Trigger | By the tenth calendar day after month end |
| Population | Every commit reachable from `origin/main` whose committer date is in the month, plus every pull request GitHub reports as merged to `main` in the month. The two lists are reconciled |
| Retirement | When a second maintainer exists and the ruleset requires one approval from a person who is not the author (with `require_last_push_approval`), the review stays as a check on the ruleset but stops being the only control |

### 3.3 Steps

1. **Population.** List commits with `git log origin/main --since=<first> --until=<next first> --format='%h|%cd|%s'` and merged pull requests with `gh pr list --state merged --search 'merged:<range>'`. Run `git fetch` first so that the local `main` is not stale. Reconcile: every commit belongs to a merged pull request; every merged pull request has a merge commit in the history. Differences are findings.
2. **Per pull request**, from `gh pr view <n> --json author,mergedBy,mergedAt,reviews,statusCheckRollup`:
   - the five required checks (`validate-scripts`, `unit-tests`, `compliance / validate`, `compliance / compliance`, `Control Validation Regression`) are successful at the head commit;
   - the ruleset existed at the merge time (compare `mergedAt` with the ruleset's `created_at` and `updated_at`);
   - author, merger and any approving reviewer are listed. Zero approvals or author equal to merger is reported as a standing finding, not repeated as a new one each month, but the counts are given;
   - for a MEDIUM decision, the `medium-risk-approval` environment history shows who approved.
3. **Sensitive paths.** List pull requests that touch `.github/`, `Internal-IT/engineering/`, `exceptions.yaml`, `control-mapping.yaml` or `CODEOWNERS`. Read their diffs. For `exceptions.yaml`, check every new or changed entry for a reason, an owner and an expiry no later than 12 months. For `control-mapping.yaml`, check that no severity was lowered.
4. **Configuration drift.** Export the ruleset (`gh api repos/<owner>/<repo>/rulesets/<id>`) and the environment protection settings, and compare with the previous month's export. Any weaker setting is a finding. This is the substitute for the audit-log alert ALR-08, which needs a GitHub plan with audit-log streaming.
5. **Pipeline health.** List the push runs on `main` for the month and their conclusion. A red or waiting run is a finding with an owner.
6. **Emergency changes.** For each change declared an emergency (change management policy, section 6), confirm that the retrospective review within two business days exists.
7. **Write the record** as `Governance/records/real/soc2/REAL-SOC2-<nnn>-change-review-<yyyy>-<mm>.md`, with the banner and fields required by the [real records rules](../records/real/README.md), the tables of pull requests and commits, the findings, and the stated limit.
8. **Act.** Findings go to the deficiency log (MO-03) with an owner and a due date, and to the quarterly management report (CE-06).

### 3.4 Pass and fail

| Result | Meaning |
|---|---|
| No finding | Every merge was through a pull request, with all required checks successful and enforced, and no sensitive-path change is unexplained. Standing findings (no independent approval) are still printed |
| Findings | Any commit without a pull request, any merge with a failed or missing required check, any weakened ruleset or any unexplained change to the gate. The review is closed only when each finding has an owner and a date |

### 3.5 Honest limit

A review run by the author is a log, not a control with separation of duties. It shows that an independent reviewer could do the same in an hour. The first instance, REAL-SOC2-001 (October 2026, performed 2026-11-10), was run by the repository owner with a tool and states this limit. Improvement that needs the owner: ask a trusted outside person, such as a peer engineer under a confidentiality agreement, to read the monthly record and the sensitive-path diffs. Until then CM-05 stays **Designed**.
