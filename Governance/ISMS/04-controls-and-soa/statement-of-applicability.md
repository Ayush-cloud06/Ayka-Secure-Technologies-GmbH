Ayka Secure Technologies GmbH is a simulated company. This is a proposed selection of controls, not certification or a record of management approval. Assessment snapshot: 2026-11-10.

## 1. Basis and decision rules

This register addresses clause 6.1.3(d) of ISO/IEC 27001:2022 against the [ISMS scope](../00-context-and-governance/scope.md), [risk register](../03-risk-management/risk-register.md), [risk treatment plan](../03-risk-management/risk-treatment-plan.md), and [legal register](../00-context-and-governance/legal-and-regulatory-register.md). The control IDs cover all 93 Annex A:2022 entries; the short working labels below describe their subject and do not reproduce normative control text. The [ISO catalogue](https://www.iso.org/standard/82875.html) identifies the management-system standard; use a licensed copy for normative assessment.

**Applicability:** Yes means selected for the proposed scope, including supplier oversight. All 93 are selected; none are excluded. Absent implementation is a gap, not a reason for exclusion. Provider facilities, remote work and prospective outsourced development retain relevant responsibilities even when Ayka does not operate the facility or currently use an external developer. Review this conservative selection when actual contracts, premises and processing are known; no exclusion is approved by this draft.

**Status**, weakest to strongest (`Planned < Designed < Gated design < Simulated operation < Partial < Implemented`, see [ADR-0006](../../ADR/0006-simulated-operating-records.md)):

- **Planned**: the control-specific design is still missing. Planned rows may link related requirements that do not yet design that control.
- **Designed**: documentation, or Terraform that no gate scans, exists. It does not mean the control operates.
- **Gated design**: the Terraform that implements the row is scanned by the compliance gate and has never been deployed. For the workload this is the CI gate. For the platform roots it is the local run in [REAL-INFRA-001](../../records/real/infra/REAL-INFRA-001-gate-run-all-roots.md) of CI jobs that have not yet run on GitHub and are not required checks.
- **Simulated operation**: a design exists and a bannered record in [`records/simulated/`](../../records/simulated/README.md) walks it from start to finish as a tabletop. The row links that record. It is not operating evidence.
- **Partial**: a named subset operates, shown by a real record or a CI run on GitHub, with remaining gaps.
- **Implemented**: operating evidence for the stated scope. Never supported by a simulated record.

A row is raised to Simulated operation only when the record's "Procedure exercised" is the row's linked design or a direct part of it. A control named in a record's Controls field is not enough. A walk-through whose own findings show the core step of the control could not be carried out (for example, no reporting channel exists) does not raise the row. Local tool runs (REAL-INFRA-001, REAL-SDLC-001, REAL-PRIV-001, REAL-INFRA-002) do not raise a row to Partial: they show a tool or method works, not that the control operates for Ayka.

The [compliance workflow](../../../.github/workflows/terraform-workflow.yml) gates `Internal-IT/workloads/ayka-portal` in CI. Its refresh-free plan and simulated apply are not runtime evidence. From 2026-11-10 the pipeline also defines platform jobs (plan mode: `aws-organization`, `landing-zone`, `evidence-archive`, `aws-iam-core`; source mode without the OPA rules: `remote-state`, `aws-identity-center`; Entra ID validate-only, because no scanner has rules for it). A mapping ID denotes a repository cross-reference, not satisfaction of the whole Annex A control. The [gap analysis](control-gap-analysis.md) explains these limits. RISK-011: the Terraform source now names only `eu-central-1` ([REAL-INFRA-003](../../records/real/infra/REAL-INFRA-003-region-migration-verification.md)); the residency decision and the re-creation of the Identity Center instance remain open.

## 4. How to read the counts

The status "Simulated operation" was added by [ADR-0006](../../ADR/0006-simulated-operating-records.md). It means a procedure has been walked from start to finish on paper, with fictional staff, and the walk-through is filed as a bannered record. Nothing happened. Its value is that it shows the procedure can be followed and where it breaks: every simulated record ends with findings, and those that are true of the repository are in the [improvement register](../11-improvement/improvement-register.md).

The honest reading of the 93 rows on 2026-11-10:

- **Real evidence: 7 rows (Partial).** The CI gate runs on GitHub on every pull request, the ruleset enforces it, the evidence bundle and inventory come from CI runs, and REAL-SOC2-001 lists October's changes from GitHub. Each of these covers a named subset only. No row is Implemented.
- **Scanned Terraform, never deployed: 11 rows (Gated design).** Seven rest on the workload gate in CI. Four (A.5.23, A.5.33, A.8.3, A.8.31) rest only on the platform roots, whose CI jobs have not yet run on GitHub and are not required checks.
- **Walked only in simulation: 30 rows (Simulated operation).** Some also have a real local test of a tool or method (REAL-INFRA-002 restore on a local container, REAL-PRIV-001 DSR tool on fixtures, REAL-SUP-001 public supplier pages). None of those is operation of the control for Ayka.
- **Design only: 45 rows (Designed).** A.5.3 moved down from Partial: real evidence (REAL-SOC2-001) shows no independent approval, so no part of separation of duties operates.

So 48 rows have something beyond a document, and 7 of them rest on real operation. Neither a scan of unapplied Terraform nor a walk-through is evidence that the control works.
