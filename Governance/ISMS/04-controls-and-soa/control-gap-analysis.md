Ayka Secure Technologies GmbH is simulated. This analysis describes repository evidence and proposed treatments as of 2026-11-10; it does not record completed control operation. Simulated records ([ADR-0006](../../ADR/0006-simulated-operating-records.md)) show that a procedure can be walked; they close no gap.

## 1. What the gate can establish

The [SoA](statement-of-applicability.md) selects 93 Annex A controls. The [gate metadata](../../../Internal-IT/engineering/policy-as-code/metadata/control-mapping.yaml) contains 38 internal control IDs referencing 16 distinct Annex A IDs. The other 77 IDs have no explicit gate metadata mapping. This is a traceability count, not a measure of compliance: code checks cannot evaluate employee agreements, actual incident handling, supplier contracts or management decisions.

The [workflow](../../../.github/workflows/terraform-workflow.yml) validates and scans the `ayka-portal` workload plan and source, evaluates findings and writes evidence. A local run of the full chain at commit `bc11890` on 2026-11-10 planned 97 resources and decided pass with 6 LOW findings and 15 excepted findings (set aside by 14 entries in `exceptions.yaml`). See the [S3 control chain](control-chain-s3-encryption.md) for a dated test/run example. A finding can be absent because a resource is absent, excluded, unrecognized or outside scanner scope. A pass therefore does not establish every mapped control. Review resource coverage, scanner completion, exceptions and decision details in the evidence bundle.

Since 2026-11-10 the pipeline defines platform jobs. [REAL-INFRA-001](../../records/real/infra/REAL-INFRA-001-gate-run-all-roots.md) ran them locally: plan mode for `aws-organization` (10 resources), `landing-zone` (183), `evidence-archive` (14) and `aws-iam-core` (20), all pass; source mode without the OPA rules for `remote-state` and `aws-identity-center`, both pass; Entra ID is refused by the evaluator because no scanner has rules for it, so CI only validates it. `exceptions.yaml` now holds 111 entries, each scoped to one root (14 for `ayka-portal`, 97 for the platform roots), with expiries from 2027-01-08 to 2027-11-26. Some are real open work (broad IAM grants in `aws-iam-core`, no access logging on the log, state and evidence buckets, shared-key auth on the Azure state account). The platform jobs have not yet run on GitHub and are not required checks, so a red platform job does not block a merge. The [identity mapping](iam-iso27001-mapping.md) is source design, not validated federation. Plans use mock credentials and refresh disabled; apply is simulated. No runtime logs, restore of a real backup or effective-permissions verification is established by these artifacts. [REAL-INFRA-002](../../records/real/infra/REAL-INFRA-002-restore-test-local-postgres.md) tested the restore-and-verify method on a local PostgreSQL container only. The [risk register](../03-risk-management/risk-register.md) records these limits as RISK-003, RISK-006, RISK-007, RISK-008 and RISK-012.

In particular, public-access/ACL checks are not cryptographic proof; unused security groups are not access-review or logging evidence; rule descriptions are not operating procedures; Terraform IAM-user findings do not verify a real MFA challenge.

## 4. Status corrections and review

The [risk register](../03-risk-management/risk-register.md) records GitHub API verification on 2026-10-14: active ruleset `protect-main` (ID 24482491) requires a pull request and five checks, but zero approving reviews. Both `manual-apply-approval` and `medium-risk-approval` require the maintainer as reviewer and allow self-review (`prevent_self_review=false`). These settings provide limited change gating, not independent separation of duties. RISK-005 remains Treating; no production approval or independent second review is evidenced. [REAL-SOC2-001](../../records/real/soc2/REAL-SOC2-001-change-review-2026-10.md) confirms this for October 2026: 17 of 17 merged pull requests passed the five required checks, 15 of them under the ruleset, and none had an approval. The SoA therefore lowers A.5.3 from Partial to Designed in version 1.2.

Review gaps when evidence changes, after incidents and at least annually after approval. Keep the [SoA](statement-of-applicability.md), [risk register](../03-risk-management/risk-register.md), [evidence index](../07-technical-evidence/control-evidence-index.md) and [improvement register](../11-improvement/improvement-register.md) consistent. CISO proposes closure; the responsible owner supplies evidence and management records any residual acceptance. The current documentation completion does not close these operating gaps, and no gap closes on simulated records alone (ADR-0006).
