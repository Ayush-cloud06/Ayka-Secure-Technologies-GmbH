## Scenario summary

The 24 people in the [personnel register](../../../../organization/personnel-register.md) started between 2026-01-01 and 2026-02-13. The ISMS policies were approved on 2026-03-02 (SIM-GOV-001). 1. **Phase A, on the start date.** Entra account, mail and collaboration tools. Confidentiality clause in the employment contract. Screening done before the start date.

Screening before 2026-01-25 was done by EMP-001, because EMP-012 had not started. On 2026-03-09 EMP-002 reviewed all files against the screening criteria. The review found two gaps, both in table 1: no second reference for EMP-002, and the reference for EMP-014 arrived on 2026-03-10.

Access held before the Phase B dates, under informal arrangements before the ISMS existed, is not recorded in this file.

## Findings

1. **Three different timings for training before access.** The [access control policy](../../../policies/access-control-policy.md) section 4.4 asks for completed baseline training before the first working day. The [training programme](../../../../organization/training-and-awareness.md) says before production access. The onboarding procedure says before access. "Production access" is not defined. This walk-through treated Entra and mail as outside it and Identity Center and GitHub as inside it.
2. **No transition rule for people hired before the procedures.** Every procedure starts "on approval". Nothing says how staff already employed are brought in. A retrospective review (2026-03-09) was improvised.
3. **Acknowledgement record has no field list.** The onboarding procedure asks for "policy acknowledgement" as evidence. It does not say which policy version, which date, or what counts as acknowledged. The AUP says the onboarding procedure supplies the record; it does not.
4. **No code of conduct.** SOC 2 CE-02 needs acknowledgement of a code of conduct and the AUP at hire and yearly. No code of conduct exists. The column in table 2 is empty for all 24. Whoever writes it must also set the acknowledgement date, then CE-02 can be walked again.
5. **Right-to-work check is in the Tier 2 row only.** The screening criteria list it for "Tier 2 and other staff" and omit it for Tier 0 and Tier 1. The law applies to all employees. HR did it for everyone.
6. **Screening independence has no answer for the top of the company.** EMP-001 has no reviewer. EMP-002's file was reviewed by EMP-001, who is not a security reviewer. The criteria say the CISO confirms Tier 0 before a privileged account is requested, which here means EMP-002 confirming her own screening.
7. **No step compares a Tier 0 request with the cap.** The access control policy limits Tier 0 to the CISO and at most two Cloud Platform engineers. The identity source puts EMP-001 in Identity Center Tier0. It also puts all four admin accounts (EMP-002, EMP-003, EMP-013, EMP-014) into Entra `grp-tier-tier0`. The [user access procedure](../../../ISMS/06-operational-procedures/user-access-procedure.md) has no check against the cap, and the justification register has no "count of members" field.
8. **Admin and daily accounts are not kept apart in Identity Center.** `memberships.tf` puts the ordinary accounts of EMP-003, EMP-013 and EMP-014 in Tier1 and lists no admin account for them in Tier0. The admin accounts have no stated use.
9. **No tier means "no AWS access".** All 18 people in Tier 2, including HR, finance, marketing and sales staff, receive the Tier2-Workload permission set. The policy describes Tier 2 as developers. The user access procedure says "minimum access" but the group model cannot express it.
10. **GitHub is outside the personnel source.** Team membership is granted by hand. The user access procedure says GitHub access is not proven by an Entra diff, but gives no source list for GitHub and no joiner field for it.
11. **MFA prerequisite cannot be shown.** The user access procedure asks to confirm MFA capability. Conditional Access defaults to off in source (`enable_conditional_access = false`), and no field says where MFA enrolment is recorded. The Tier 0 phishing-resistant key issue (access policy 4.2) has no asset record either.
12. **A non-privileged Tier 1 member needs no justification.** EMP-004 is in Tier1 without the privileged flag, so the justification step was not triggered. The step should trigger on the group, not on the flag.
13. **Approver for the Managing Director.** The procedure says to escalate to the Managing Director where roles overlap. When the requester is the Managing Director there is no one to escalate to. EMP-002 approved, but she reports to him.
14. **Register and identity source disagree on who is privileged.** Register: EMP-003 and EMP-013. Identity fixture: EMP-002, EMP-003, EMP-013, EMP-014. Identity Center: EMP-001 in Tier0.

## What this does not show

- That any account, group or permission existed in a real tenant. The identity Terraform has never been applied.
- Any real screening result, reference, identity document or contract.
- Who actually used which access before the Phase B dates.
- A reconciled lifecycle between HR, Entra, Identity Center and GitHub (RISK-004).
- That a person understood the policies they acknowledged. Understanding is measured in SIM-PPL-003 only by completion and one quiz.
